### 2.问题分析

### A. 执行与自我管理

- 计划与实际执行存在较大偏差。
- 执行力不足，容易拖延、偷懒，并为不执行寻找合理化理由。
- 对时间的支配、分配和管理能力不足。
- 对手机、娱乐、饮食等即时满足行为的控制能力不足。

### B. 认知与行为

- 存在明显的“知行不一”。
- 已经认识到某些事情应该做，但认知不能稳定转化为实际行动。
- 动力具有波动性，存在“知道重要但没有行动欲望”的情况。

### C. 注意力与精神状态

- 当前专注力属于一般水平，希望达到非常高的水平。
- 容易浮躁，难以长期保持安静、沉浸和稳定的心理状态。
- 希望逐渐获得独处、寂寞和安静状态下持续工作的能力。

### D. 长期能力成长

用户不仅希望“完成更多任务”，而是希望真正改变自身能力，包括：

- 自控力
- 执行力
- 学习能力
- 问题分析能力
- 时间管理能力
- 沟通表达能力
- 科研能力
- 创新能力
- 生活管理能力
- 身体管理能力
- 认知与行为能力

降低和逐步解决：

其目的不是永远替用户做决定，而是随着时间推移，**越来越强地培养用户本人**。

## 3. 使用需求



### 3.1 日常记录

**FR-001**
 系统应支持用户记录一天的实际成果。

**FR-002**
 系统应支持用户从多个生活/成长领域记录当天成果，而不是只能记录学习。

**FR-003**
 系统应保存历史记录，使用户能够回顾过去任意一天的情况。

**FR-004**
 系统应允许用户补充或修正当天记录。

### 3.2 日常辅助

**FR-005**
 系统应能够向用户呈现当前阶段需要完成的事项。

**FR-006**
 系统应能够让用户快速查看当前目标、当前任务及其上下文。

> 用户明确说的是“临时看一下”。

属于**低成本、快速获取信息**的使用场景。

### 3.3 动力与行动辅助

**FR-007**
 系统应支持用户在动力不足时主动调用系统。

**FR-008**
 系统应能够向用户呈现与当前行动相关的目标、计划、进展等信息，以辅助用户恢复行动意愿。

现在只规定**系统要提供这种能力**，还没有规定“采用激励语录、心理学方法还是其他机制”。

### 3.4 方向导航

**FR-009**
 系统应支持用户在方向不明确时查询自身当前的目标与发展方向。

**FR-010**
 系统应能够将当前行动与长期目标建立关联，使用户能够理解：

> “我现在做的事情，为什么值得做？”



### 3.5 决策辅助

**FR-011**
 系统应支持用户提交重大决策情境。

**FR-012**
 系统应能够基于用户已有的目标、原则、约束、历史信息和相关记录，为决策提供分析参考。

**FR-013**
 系统提供的是**决策辅助**，而不是代替用户进行最终决定。

### 3.6 计划与监督

**FR-014**
 系统应支持制定阶段性及短期计划。

**FR-015**
 系统应支持将计划与实际执行结果进行对照。

**FR-016**
 系统应能够识别计划与实际执行之间的偏差。

**FR-017**
 系统应能够对执行偏差进行分析。

### 3.7 调整与复盘

**FR-018**
 系统应支持根据实际执行结果调整后续计划。

**FR-019**
 系统应支持日、周、月及更长期限的复盘。

**FR-020**
 系统应能够识别长期趋势，而不仅仅分析单日表现。

### 3.8 自维护与迭代

**FR-021**
 系统应能够发现自身规则、计划或管理方式存在的问题。

**FR-022**
 系统应能够提出系统调整建议。

**FR-023**
 系统应支持对调整方案进行验证。

**FR-024**
 系统应支持系统版本的更新，并保留历史版本。

**FR-025**
 系统应支持长期维护自身运行所需的信息、规则和结构。

## 4.非功能需求

### NFR-01 可持续性

系统必须适合长期、日常、连续运行。

核心要求：

> **维护系统的成本不能高到反过来影响用户正常生活。**

系统不能成为新的负担。

------

### NFR-02 低使用摩擦

高频操作必须简单、快速。

特别的，对于：

日终记录

查看当天任务

快速查看长期方向

动力不足时调用

临时查询当前状态

原则：

> **调用系统的成本必须低于它带来的收益。**

------

### NFR-03 适应性与容错性

系统必须适应现实世界的不确定性。

包括：

- 临时事件
- 计划延期
- 状态波动
- 学习效率变化
- 考试周
- 旅行
- 生病
- 阶段性目标变化

必须遵循：

> **计划可以失败，系统不能因为计划失败而失效。**

------

### NFR-04 可解释性

系统的重要判断、建议和调整必须尽可能能够回答：

> **为什么？**

尤其包括：

- 为什么这样安排？
- 为什么判断这是一个问题？
- 为什么建议修改计划？
- 为什么认为某种方法更合适？

不能形成不可解释的“黑箱指导”。

------

### NFR-05 可追溯性

系统的重要状态变化必须能够追溯。

例如：

> v1.2 为什么变成 v1.3？

需要能够追溯：

**历史数据 → 发现的问题 → 分析 → 决策 → 修改内容 → 修改结果**

这样系统才真正具备工程意义上的维护和演化能力。

------

### NFR-06 用户主权与可控性

这是 Personal OS 的**最高优先级非功能要求之一**。

系统始终服务于用户，而不是反过来控制用户。

必须保证：

> **用户拥有最终决定权。**

尤其是：

- 核心人生目标
- 核心价值
- 重大人生选择
- 重要规则

AI 可以：

**分析 → 提议 → 论证**

但不能：

**擅自决定 → 强制执行。**

------

### NFR-07 可靠性、恢复性与稳定性

系统必须能够承受失败。

例如：

> 连续三天没有完成计划。

系统不能因此进入“系统崩溃”状态。

而应该：

> 发现异常 → 分析原因 → 进入恢复模式 → 恢复正常运行。

同时，已经验证有效的稳定规则不能因为一次异常就随意改变。

------

### NFR-08 隐私与数据安全

Personal OS 会积累非常大量的个人信息，因此必须把：

> **数据最小化、隐私保护、访问控制、历史数据保护**

作为基础要求。

尤其应该避免：

> 为了方便 AI 工作而无必要地收集大量个人信息。

------

### NFR-09 可维护与可演化

系统必须允许长期变化：

- 增加新的管理领域
- 删除无效模块
- 修改规则
- 替换策略
- 增加新的数据来源
- 修改目标
- 升级版本

但是变化必须：

> **有记录、有原因、有版本、有回滚能力。**

也就是说：

**系统必须允许改变，但不能无序地改变。**

------

### NFR-10 以人为本与能力成长

这是根据你的核心目标，我认为必须加入的一条，而且它实际上属于**系统级非功能原则**。

系统运行的长期效果应该是：

> **用户自身能力增强，而不是用户对系统的依赖增强。**

因此系统需要长期关注：

```
自控力 ↑
执行力 ↑
计划能力 ↑
时间管理能力 ↑
专注能力 ↑
问题分析能力 ↑
独立决策能力 ↑
```

而不是单纯追求：

> “每天使用 AI 的次数越来越多。”

这是 Personal OS 与普通效率工具的根本区别之一。

### NFR-11 系统边界与约束

 

> **Personal OS 负责**

- 长期目标与阶段目标管理
- 学习与能力成长
- 时间与任务管理
- 作息管理
- 饮食与运动管理
- 科研、创新、阅读、写作、表达、沟通等个人发展
- 日常记录与复盘
- 执行监督与偏差分析
- 计划与策略调整
- 个人行为、习惯和能力的长期趋势分析
- 系统自身维护、实验、版本管理与迭代

> **不属于 Personal OS 的职责**

- 医疗诊断系统
- 心理疾病诊断系统
- 法律顾问
- 财务顾问
- 替用户做重大人生决定的代理人
- 完全自动控制用户行为的系统

涉及这些领域时，它最多提供**信息整理和决策辅助**，不能把自己定义成专业替代品。

## **2.1 总体架构**

Personal OS 的核心运行闭环：

**目标 → 状态 → 决策 → 计划 → 行动 → 记录 → 反馈 → 调整**

```text
                    PERSONAL OS
                         │
          ┌──────────────┴──────────────┐
          ↓                             ↓
      Core / Goals                  AI Engine
          ↓
        State
          ↓
  Decision / Planning
          ↓
      Execution
          ↓
 Feedback / Logging
          ↓
 Evaluation / Review
          ↓
      Evolution
          │
          └──────────────→ Strategy
```

<b>上层约束下层，下层不能随意改变上层</b>

### **2.1.1 Core**

回答：

> **我为什么这样生活？**

包含最稳定的内容：

- 核心价值
- 基本原则
- 长期方向
- 底线

这一层修改频率最低。

------

### **2.1.2 Goal & Strategy**

回答：

> **我现在要往哪里走？**

包括：

- 长期目标
- 年度目标
- 季度目标
- 月度目标
- 阶段策略
- 当前优先级

------

### **2.1.3 State**

回答：

> **我现在是什么状态？**

包括：

- 睡眠
- 精力
- 专注
- 学习进度
- 时间资源
- 体能
- 执行稳定性

State 是系统对现实状态的描述。

------

### **2.1.4 Decision & Planning**

回答：

> **根据我的目标和当前状态，我现在应该怎么安排？**

负责产生：

- 日计划
- 周计划
- 学习安排
- 运动安排
- 时间调度
- 动态调整

------

### **2.1.5 Execution & Logging**

回答：

> **现实中到底发生了什么？**

负责：

- 任务执行
- 行动记录
- 每日成果记录
- 事件记录
- 实际结果记录

这是系统获得现实反馈的主要入口。

------

### **2.1.6 Evaluation & Evolution**

回答：

> **系统现在做得对不对？要不要改变？**

包括：

- 日复盘
- 周复盘
- 月复盘
- 趋势分析
- 问题诊断
- 实验
- 策略修改
- 系统版本升级

最终反馈至 Strategy。

------

### **2.1.7 总体架构原则**

**上层约束下层，下层不能随意改变上层。**

```
Core
 ↓
Goals
 ↓
Strategy
 ↓
Plan
 ↓
Execution
```

例如：

- 单次计划失败，不能直接修改长期目标。
- 短期情绪波动，不能直接修改核心原则。
- 长期数据证明策略不合理，可以调整 Strategy。
- 越靠近 Core，修改权限越低。
- 越靠近 Execution，允许越灵活调整。

### **2.2.1 Core & Goal System**

#### **2.2.1.1 职责**

回答：

> **我为什么这样生活？**
>
> **我要去哪里？**
>
> **现阶段什么最重要？**

本子系统是 Personal OS 的最高层之一。

------

#### **2.2.1.2 内部组成**

```
Core & Goal System
│
├── A. Core Values
│   └── 核心价值
│
├── B. Principles
│   └── 长期原则 / 底线
│
├── C. Goals
│   └── 长期 → 中期 → 短期目标
│
└── D. Priorities
    └── 当前阶段优先级
```

------

### **2.2.2Core Values**

定义：

> **我为什么想成为这样的人？**

Core Values 属于用户本人，不由 AI 代替定义。

特点：

- 稳定
- 修改频率低
- 修改需要用户主动确认

------

### **2.2.3Principles**

回答：

> **在追求目标的过程中，我坚持什么？**

原则用于约束系统和用户行为。

例如：

- 不用长期牺牲健康换取短期成绩。
- 不因短期情绪轻易修改长期目标。
- 优先保证最重要的事情。
- 系统可以建议，但最终决定权属于用户。

------

### **2.2.4 Goals**

目标采用层级结构：

```
Vision
 ↓
Long-term Goals
 ↓
Annual Goals
 ↓
Quarterly Goals
 ↓
Monthly Goals
 ↓
Weekly Goals
```

目标之间形成目标链，而不是互相独立的目标列表。

例如：

```
长期目标
 ↓
年度目标
 ↓
季度目标
 ↓
月度目标
 ↓
周目标
```

这样系统能够回答：

> **“我今天做的事情，和我的长期目标有什么关系？”**

------

### **2.2.5Priorities**

目标之间存在资源竞争，因此必须存在优先级。

优先级考虑：

- 重要性
- 紧迫性
- 长期价值
- 当前阶段

优先级允许根据当前阶段动态调整。

------

### **2.2.6目标与计划的分离**

**目标 ≠ 计划**

例如：

> “每天学习 4 小时”

属于计划。

而：

> “在规定时间前达到目标院校要求的能力水平”

属于目标。

设计原则：

> **目标保持方向稳定，计划与策略允许调整。**

因此：

```
计划失败
↓
分析原因
↓
调整计划 / 策略
↓
继续追踪目标
```

而不是：

```
计划失败
↓
认为目标失败
```

------

### **2.2.7输出**

Core & Goal System 向下层提供：

- Core Values
- Principles
- Goals
- Goal Hierarchy
- Current Priorities
- 与目标相关的约束

然后交给：

**Personal State System + Planning System**

------

### **2.2.8修改权限**

| 对象            | 修改方式           |
| --------------- | ------------------ |
| Core Values     | 用户主动修改       |
| Principles      | 用户确认后修改     |
| Long-term Goals | 用户主导，AI辅助   |
| 阶段目标        | AI可提出调整       |
| Priorities      | 可根据阶段动态调整 |
| Daily Plan      | 不属于本层         |

基本原则：

> **越靠近 Core，修改权限越低；越靠近 Execution，调整越灵活。**





## **2.3 核心数据模型**

> 本节定义 Personal OS 的核心数据实体及其关系。
>
> 当前阶段只确定**概念数据模型**，暂不确定具体数据库表结构、字段类型和技术实现。

### **2.3.1 数据模型总体结构**

Personal OS 的核心数据可以分为 7 个层次：

```text
Core
 ↓
Goals / Priorities
 ↓
State / Resources / Constraints
 ↓
Strategy / Policy
 ↓
Plan
 ↓
Execution / Events
 ↓
Feedback / Review
 ↓
Decision / Experiment
 ↓
Version / Evolution
```

### **2.3.2 核心数据实体**

#### **A. Core 层**

##### **1. CoreValue（核心价值）**

描述用户希望长期坚持的价值取向。

例如：

- 成长
- 自主
- 求知
- 健康
- 长期主义

特点：

- 稳定
- 修改频率低
- 用户拥有最终修改权

------

##### **2. Principle（原则）**

描述用户在实现目标过程中应遵守的长期原则与底线。

例如：

- 不以长期健康换取短期成果。
- 不因短期情绪轻易改变长期方向。
- 计划服务于目标，而不是目标服务于计划。

------

#### **B. Goal 层**

##### **3. Goal（目标）**

描述用户希望达到的结果。

目标具有层级关系：

```
Vision
 ↓
Long-term Goal
 ↓
Annual Goal
 ↓
Quarterly Goal
 ↓
Monthly Goal
 ↓
Weekly Goal
```

一个目标可以由多个下级目标支撑。

------

##### **4. Priority（优先级）**

描述当前阶段目标、项目或任务之间的重要程度。

优先级可以动态变化，但必须能够记录：

- 当前优先级
- 调整原因
- 生效时间

------

#### **C. State 层**

##### **5. StateSnapshot（状态快照）**

描述用户在某一时间点的状态。

包括但不限于：

- 睡眠
- 精力
- 专注
- 学习状态
- 身体状态
- 执行状态
- 时间可用量

状态是动态数据，需要随着时间持续变化。

------

##### **6. Resource（资源）**

描述用户当前可利用的资源。

包括：

- 时间
- 精力
- 金钱
- 工具
- 信息
- 空间
- 其他可利用资源

------

##### **7. Constraint（约束）**

描述计划和决策必须遵守的现实限制。

包括：

- 固定时间安排
- 学业/工作安排
- 预算
- 环境限制
- 身体限制
- 其他不可忽略的现实条件

------

#### **D. Strategy 层**

##### **8. Strategy（策略）**

描述为了实现某个目标，在当前状态和约束下采用的总体方法。

例如：

```
Goal：
提高专业课成绩

Strategy：
建立知识体系
→ 间隔复习
→ 题目训练
→ 阶段测试
```

策略允许根据长期反馈进行修改。

------

##### **9. Policy（策略规则）**

描述在特定状态下应采取什么行动。

形式：

```
IF 状态满足条件
THEN 执行对应策略
```

例如：

```
IF 连续多日执行率下降
THEN 进入问题诊断
```

Policy 是 Personal OS 实现动态调整的重要数据。

------

#### **E. Planning 层**

##### **10. Plan（计划）**

描述某一时间范围内准备完成的事项。

层级：

```
Monthly Plan
 ↓
Weekly Plan
 ↓
Daily Plan
```

计划由 Goals、State、Strategy 和 Constraints 共同影响。

------

##### **11. Project（项目）**

描述具有明确目标、周期和成果的较大任务集合。

例如：

- 考研准备
- 某科研项目
- 某课程体系学习
- 某长期个人项目

Project 可以包含多个 Task。

------

#### **F. Execution & Feedback 层**

##### **12. Task（任务）**

描述可以被执行和完成的具体事项。

Task 可以来自：

- Plan
- Project
- Habit
- 临时事件

Task 应能够记录：

- 计划状态
- 实际状态
- 完成情况
- 时间
- 偏差

------

##### **13. Habit（习惯）**

描述需要长期重复执行的行为模式。

例如：

- 固定睡眠
- 每日学习
- 每周运动
- 每日阅读

Habit 与 Task 不同：

> Task 是一次具体行动，Habit 是长期重复行为。

------

##### **14. Event（事件）**

描述现实世界中实际发生的重要事件。

例如：

- 完成一次学习
- 临时事务
- 计划中断
- 睡眠异常
- 情绪波动
- 重要决策
- 重大变化

Event 是系统记录现实世界变化的重要数据。

------

##### **15. Observation（观察记录）**

描述系统或用户对现实情况的观察。

例如：

```
观察：
连续一周下午学习效率下降。
```

Observation 不应直接等同于结论。

------

##### **16. Metric（指标）**

描述可以被持续观察的量化或半量化指标。

例如：

- 学习时间
- 计划完成率
- 睡眠时长
- 运动次数
- 手机使用时间
- 任务延期率

Metric 用于长期趋势分析。

------

#### **G. Evaluation & Evolution 层**

##### **17. Review（复盘）**

描述对过去一段时间的系统性评估。

层级：

```
Daily Review
 ↓
Weekly Review
 ↓
Monthly Review
 ↓
Quarterly Review
```

Review 用于：

- 分析结果
- 发现问题
- 判断趋势
- 提出调整

------

##### **18. Decision（决策）**

记录重要决策及其依据。

包括：

- 决策内容
- 决策背景
- 使用的信息
- 考虑的因素
- 最终结果

用于长期追踪：

> 为什么当时做出了这个决定？

------

##### **19. Experiment（实验）**

用于验证新的策略、方法或规则。

基本结构：

```
假设
 ↓
实验方案
 ↓
执行
 ↓
数据
 ↓
结果
 ↓
结论
```

只有经过验证的实验结果，才考虑进入正式策略。

------

##### **20. Version（版本）**

描述 Personal OS 自身的版本变化。

例如：

```
Personal OS v1.0
Personal OS v1.1
Personal OS v2.0
```

每次重要系统修改都应产生版本记录。

------

##### **21. ChangeLog（变更记录）**

记录系统为什么发生变化。

基本关系：

```
问题
 ↓
分析
 ↓
决策
 ↓
修改
 ↓
新版本
 ↓
结果
```

用于保证系统的可追溯性。

------

### **2.3.3 核心实体关系**

Personal OS 的核心关系可以抽象为：

```

   ↓

   ↓

   ↓

   ↓

   ↓

```

### **2.3.5 数据模型设计原则**

#### **原则 1：事实与推论分离**

系统必须区分：

```
Fact
Observation
Inference
Hypothesis
Decision
Result
```

不能把推测直接当成事实。

------

#### **原则 2：目标与计划分离**

Goal 描述：

> 想达到什么。

Plan 描述：

> 准备怎么达到。

计划可以变化，目标不应因为一次计划失败而自动改变。

------

#### **原则 3：状态与评价分离**

State 描述：

> 现在是什么状态。

Review 描述：

> 对这个状态进行怎样的评价。

避免把主观评价直接当成客观状态。

------

#### **原则 4：现实记录不可被系统随意修改**

历史 Event、Observation、Metric 等数据原则上应保留原始记录。

后续修正应该留下修改痕迹。

------

#### **原则 5：系统变化必须可追溯**

任何重要 Strategy、Policy 或规则的变化，都应能够追溯到：

```
原状态
→ 问题
→ 原因
→ 决策
→ 修改
→ 新版本
→ 修改后的结果
```

------

#### **原则 6：数据模型服务于系统，不反过来增加负担**

不应为了收集数据而收集数据。

只有能够帮助：

- 决策
- 执行
- 复盘
- 诊断
- 迭代

的数据，才有必要长期保留。

这一版先把**“系统里究竟有哪些核心对象，以及它们怎么关联”**定下来，还没有进入数据库字段级设计。

下一节 **2.4 模块职责与接口** 就可以根据这里的 21 个核心实体，进一步明确：**7 个子系统各自能读什么、能写什么、向谁提供什么、禁止做什么。**

## 2.4.模块职责与接口

本节在 **2.2 子系统划分**与 **2.3 核心数据模型**的基础上，进一步明确 Personal OS 各子系统的职责、输入、输出以及相互之间的关系。

本节暂不进入具体的 API、数据库字段或技术实现，而是首先明确：

> **每个模块负责什么？**
>
> **每个模块可以使用什么数据？**
>
> **每个模块产生什么数据？**
>
> **模块之间如何协作？**

### **2.4.1 模块总体结构**

Personal OS 包含 7 个核心子系统：

```text
Personal OS
│
├── 1. Core & Goal System
│
├── 2. Personal State System
│
├── 3. Planning System
│
├── 4. Execution System
│
├── 5. Feedback System
│
├── 6. Review & Decision System
│
└── 7. Evolution System
```

同时，系统具有一个贯穿各个子系统的：

```text
AI Engine
```

AI Engine 不作为独立的业务子系统，而是作为整个 Personal OS 的智能分析与辅助能力。

系统整体关系可以表示为：

```text
Core & Goal
      ↓
State
      ↓
Strategy / Policy
      ↓
Planning
      ↓
Execution
      ↓
Feedback
      ↓
Review & Decision
      ↓
Evolution
      ↓

      ↓
重新进入 Planning
```

其中：

> **上层约束下层，下层不能随意改变上层。**

------

### **2.4.2 Core & Goal System**

#### **2.4.2.1 职责**

Core & Goal System 负责定义 Personal OS 最上层的方向与约束。

主要回答：

> **我为什么这样生活？**

> **我要去哪里？**

> **当前阶段什么最重要？**

负责管理：

- CoreValue
- Principle
- Goal
- Priority

其中 CoreValue 和 Principle 属于整个系统中最稳定的内容。

------

#### **2.4.2.2 主要输入**

主要输入包括：

- 用户主动输入
- 已有 CoreValue
- 已有 Principle
- 历史 Goal
- 历史 Priority
- 系统历史版本

------

#### **2.4.2.3 主要输出**

向其他系统提供：

- Core Values
- Principles
- Goals
- Goal Hierarchy
- Current Priorities
- 与目标相关的约束

主要提供给：

- Personal State System
- Planning System
- Review & Decision System
- Evolution System

------

#### **2.4.2.4 修改原则**

```text
CoreValue
    ↓
Principle
    ↓
Long-term Goal
    ↓
阶段 Goal
    ↓
Priority
```

越接近 Core，修改权限越低。

因此：

- CoreValue：用户主动修改。
- Principle：用户确认后修改。
- Long-term Goal：用户主导，AI 辅助。
- 阶段 Goal：AI 可以提出调整建议。
- Priority：可以根据当前阶段动态调整。

------

#### **2.4.2.5 模块边界**

Core & Goal System 不负责：

- 制定具体日计划。
- 记录实际执行。
- 根据一次失败自动降低长期目标。
- 因短期情绪自动修改核心原则。

其核心原则仍然是：

> **目标保持方向稳定，计划与策略允许调整。**

------

### **2.4.3 Personal State System**

#### **2.4.3.1 职责**

Personal State System 负责描述：

> **用户当前是什么状态。**

主要管理：

- StateSnapshot
- Resource
- Constraint

同时负责形成状态随时间变化的记录。

------

#### **2.4.3.2 主要输入**

主要输入包括：

- 用户主动记录
- Event
- Observation
- Metric
- 历史 StateSnapshot
- 时间资源变化
- 现实约束变化

------

#### **2.4.3.3 主要输出**

向 Planning System 与 Review & Decision System 提供：

- Current State
- State Trend
- Resource 状态
- Constraint 状态

例如：

```text
当前状态
├── 睡眠
├── 精力
├── 专注
├── 学习状态
├── 身体状态
├── 执行状态
└── 时间可用量
```

------

#### **2.4.3.4 设计原则**

Personal State System 必须区分：

```text
事实
↓
观察
↓
状态描述
↓
评价
```

例如：

```text
事实：
过去 7 天平均睡眠 6.5 小时

观察：
下午学习完成率下降

状态：
当前恢复状态可能不足

评价：
当前学习执行稳定性下降
```

不能直接将：

> “今天很懒”

作为一个客观 State 保存。

------

### **2.4.4 Planning System**

#### **2.4.4.1 职责**

Planning System 负责：

> **根据目标、状态、策略和现实约束，形成可以执行的计划。**

主要管理：

- Plan
- Project
- Task 的计划部分

计划层级包括：

```text
Monthly Plan
    ↓
Weekly Plan
    ↓
Daily Plan
```

------

#### **2.4.4.2 主要输入**

Planning System 主要读取：

- Goal
- Priority
- State
- Resource
- Constraint
- Strategy
- Policy
- 历史执行结果
- 历史 Review

因此：

> **计划不是凭空生成的，而是目标、现实状态、策略和约束共同作用的结果。**

------

#### **2.4.4.3 主要输出**

输出：

- Plan
- Project
- Task

基本关系：

```text
Goal
 ↓
Strategy
 ↓
Plan
 ↓
Project
 ↓
Task
```

------

#### **2.4.4.4 动态调整**

Planning System 可以根据现实状态变化动态调整计划。

例如：

```text
原计划
 ↓
现实状态变化
 ↓
重新计算资源
 ↓
调整任务顺序 / 时间 / 数量
 ↓
形成新计划
```

但是：

> **计划调整不等于目标调整。**

如果计划持续失败，需要进入 Review & Decision System 进行原因分析，而不能直接认为目标本身错误。

------

### **2.4.5 Execution System**

#### **2.4.5.1 职责**

Execution System 负责记录：

> **现实中到底发生了什么。**

主要涉及：

- Task
- Habit
- Event

它是 Personal OS 与现实行动之间的主要连接层。

------

#### **2.4.5.2 主要输入**

主要输入：

- Daily Plan
- Weekly Plan
- Project
- Task
- Habit

------

#### **2.4.5.3 主要输出**

主要产生：

- 实际执行结果
- Event
- Execution Record
- Task 状态变化

例如：

```text
计划：
学习数学 2 小时

实际：
学习 1.2 小时

结果：
执行 1.2 小时
偏差 -0.8 小时
```

Execution System 首先负责记录事实，而不是立即解释原因。

------

#### **2.4.5.4 Task 状态**

Task 至少应支持：

```text
Planned
↓
Started
↓
Completed
```

同时应允许：

```text
Delayed
Skipped
Cancelled
Interrupted
Partial
```

这样系统可以区分：

- 没有执行。
- 执行了一部分。
- 延期执行。
- 因外部事件中断。
- 主动取消。

------

#### **2.4.5.5 Habit 与 Task**

两者需要严格区分：

```text
Task
=
一次具体行动

Habit
=
长期重复行为模式
```

Habit 可以产生 Task，但 Habit 本身不是一次性的 Task。

------

### **2.4.6 Feedback System**

#### **2.4.6.1 职责**

Feedback System 负责把现实中的执行结果整理为可以分析的数据。

主要管理：

- Event
- Observation
- Metric

核心问题是：

> **现实中发生了什么？**

------

#### **2.4.6.2 核心数据流**

```text
Execution
 ↓
Event
 ↓
Observation
 ↓
Metric
 ↓
Trend
```

例如：

```text
过去 14 天学习记录
 ↓
平均学习时间
 ↓
计划完成率
 ↓
发现下午执行率持续下降
```

------

#### **2.4.6.3 Observation 与 Metric**

Observation：

> 对某种现实情况的观察。

Metric：

> 可以持续比较的量化或半量化指标。

例如：

```text
Observation：
连续一周下午学习效率下降。

Metric：
14:00～18:00 平均计划完成率 58%。
```

两者共同构成长期反馈的数据基础。

------

#### **2.4.6.4 主要输出**

向 Review & Decision System 提供：

- Daily Data
- Weekly Data
- Monthly Data
- Trend
- Execution Deviation
- 异常变化

------

### **2.4.7 Review & Decision System**

#### **2.4.7.1 职责**

Review & Decision System 负责分析过去产生的数据。

主要回答：

> **发生了什么？**

> **为什么发生？**

> **这说明什么？**

> **现在是否需要改变？**

主要管理：

- Review
- Decision

------

#### **2.4.7.2 Review**

Review 可以按照不同时间尺度进行：

```text
Daily Review
 ↓
Weekly Review
 ↓
Monthly Review
 ↓
Quarterly Review
```

复盘不只是评价：

> “今天完成得好不好？”

而应该逐步形成：

```text
目标
 ↓
计划
 ↓
实际执行
 ↓
偏差
 ↓
原因分析
 ↓
趋势判断
 ↓
调整建议
```

------

#### **2.4.7.3 Decision**

Decision 用于记录重要决策。

至少包括：

- 决策背景
- 使用的信息
- 考虑因素
- 决策内容
- 预期结果
- 实际结果

从而使系统未来可以追踪：

> **为什么当时做出了这个决定？**

------

#### **2.4.7.4 事实、观察与假设**

Review & Decision System 必须严格区分：

```text
Fact
↓
Observation
↓
Inference
↓
Hypothesis
↓
Decision
↓
Result
```

例如：

```text
Fact：
过去 7 天平均睡眠 6.5 小时

Observation：
下午学习完成率下降

Inference：
两者可能存在关联

Hypothesis：
睡眠不足可能影响下午学习表现

Decision：
进行两周睡眠实验

Result：
等待实验结果
```

不能把：

> “可能因为睡眠不足”

直接保存为事实。

------

### **2.4.8 Evolution System**

#### **2.4.8.1 职责**

Evolution System 负责 Personal OS 自身的维护与演化。

主要涉及：

- Experiment
- Version
- ChangeLog
- Strategy 调整
- Policy 调整

主要回答：

> **这个系统本身是否需要改变？**

------

#### **2.4.8.2 核心流程**

Evolution System 不应该发现问题后立即修改系统。

标准流程应为：

```text
发现问题
 ↓
分析问题
 ↓
提出假设
 ↓
提出修改方案
 ↓
设计实验
 ↓
执行实验
 ↓
评估结果
 ↓
Decision
 ↓
修改 Strategy / Policy
 ↓
建立新 Version
```

------

#### **2.4.8.3 Experiment**

Experiment 用于验证：

- 学习方法
- 作息方法
- 运动方法
- 时间管理方法
- 行为干预
- Strategy
- Policy

基本结构：

```text
假设
 ↓
实验方案
 ↓
执行
 ↓
数据
 ↓
结果
 ↓
结论
```

只有经过验证的实验结果，才考虑进入正式 Strategy 或 Policy。

------

#### **2.4.8.4 Version**

当 Personal OS 的重要 Strategy、Policy、规则或结构发生变化时，需要产生新的 Version。

例如：

```text
Personal OS v0.1
Personal OS v0.2
Personal OS v1.0
```

版本的目的不是单纯记录“改了几次”，而是保证系统能够：

- 追踪变化
- 比较变化
- 回顾变化
- 必要时恢复旧版本

------

#### **2.4.8.5 ChangeLog**

ChangeLog 用于记录：

```text
问题
 ↓
分析
 ↓
决策
 ↓
修改
 ↓
新版本
 ↓
结果
```

因此任何重要 Strategy、Policy 或规则变化，都应该能够回答：

> **为什么改？**

> **改了什么？**

> **依据是什么？**

> **产生了什么结果？**

------

### **2.4.9 AI Engine**

#### **2.4.9.1 职责**

AI Engine 是 Personal OS 的智能能力层，而不是最高决策层。

主要负责：

- 信息整理
- 状态分析
- 问题发现
- 计划生成
- 复盘辅助
- 趋势分析
- 决策辅助
- 假设生成
- 实验设计
- 系统升级建议

------

#### **2.4.9.2 与各子系统的关系**

AI Engine 可以参与：

```text
Core & Goal System
        ↑
Personal State System
        ↑
Planning System
        ↑
Execution System
        ↑
Feedback System
        ↑
Review & Decision System
        ↑
Evolution System
```

但是：

> **AI 可以参与，不代表 AI 可以直接修改所有数据。**

------

#### **2.4.9.3 AI 的基本工作模式**

推荐采用：

```text
读取正式数据
 ↓
AI 分析
 ↓
生成 Proposal
 ↓
审核
 ↓
批准
 ↓
正式写入
```

例如：

```text
AI 分析：

过去 21 天学习计划完成率较低，
建议降低每日计划总量。

↓

Proposal

↓

Review

↓

用户确认

↓

正式修改 Strategy / Plan
```

------

### **2.4.10 模块之间的关系**

各模块之间的核心关系可以概括为：

```text
Core & Goal
    ↓
State
    ↓
Strategy / Policy
    ↓
Planning
    ↓
Execution
    ↓
Feedback
    ↓
Review & Decision
    ↓
Evolution
    ↓
Strategy / Policy
```

其中：

```text
State
Resource
Constraint
```

会持续影响：

```text
Strategy
Plan
Task
Decision
```

------

### **2.4.11 模块接口原则**

当前阶段不确定具体 API，但逻辑接口应遵循统一原则：

```text
INPUT
 ↓
VALIDATION
 ↓
PROCESS
 ↓
OUTPUT
 ↓
LOG
```

例如 Planning System：

```text
Input：
Goal
State
Strategy
Constraint

↓

Validation：
检查目标、资源与约束

↓

Process：
形成计划

↓

Output：
Plan / Project / Task

↓

Log：
记录计划形成的依据
```

这样以后即使技术实现发生变化，系统逻辑仍然保持稳定。

------

### **2.4.12 模块读写关系**

模块之间需要区分：

```text
读取权限
```

和：

```text
修改权限
```

一个模块能够读取某个对象，并不意味着它能够直接修改该对象。

例如：

```text
AI 可以读取 CoreValue
≠
AI 可以修改 CoreValue
```

同样：

```text
Execution 可以产生 Task Result
≠
Execution 可以修改 Goal
```

------

### **2.4.13 上下层修改关系**

系统必须遵循：

> **下层不能直接修改上层。**

例如：

```text
Task 执行失败
 ↓
Feedback
 ↓
Review
 ↓
Decision
 ↓
Strategy 调整
```

而不能直接：

```text
Task 执行失败
 ↓
降低 Goal
```

同样：

```text
短期情绪波动
≠
Principle 改变
```

而：

```text
长期数据持续证明 Strategy 不合理
→
进入 Review / Decision
→
必要时调整 Strategy
```

------

### **2.4.14 数据写入原则**

重要数据应遵循以下规则：

#### **原则 1：现实记录优先保持原始性**

Event、Observation、Metric、Execution Record 等历史数据原则上不能被无痕覆盖。

如果发生修正：

```text
Original Record
 ↓
Correction
 ↓
Correction Reason
```

------

#### **原则 2：重要修改必须留下记录**

任何重要修改都应能够追溯：

```text
Before
 ↓
Reason
 ↓
Decision
 ↓
After
```

最终进入：

```text
ChangeLog
```

------

#### **原则 3：系统不能为了完成率而修改事实**

例如：

```text
计划 5 小时
实际 3 小时
```

不能为了提高完成率直接修改为：

```text
计划 3 小时
实际 3 小时
```

正确做法应该是：

```text
保留原计划
 ↓
记录实际结果
 ↓
记录偏差
 ↓
分析偏差原因
 ↓
决定是否调整下一阶段计划
```

------

### **2.4.15 本节总结**

至此，Personal OS 的 7 个核心子系统职责可以概括为：

```text
Core & Goal System
=
定义方向

Personal State System
=
描述现实状态

Planning System
=
制定计划

Execution System
=
执行与记录现实行动

Feedback System
=
形成反馈数据

Review & Decision System
=
分析、复盘与决策辅助

Evolution System
=
实验、维护与系统迭代

AI Engine
=
提供智能分析与辅助能力
```

整个系统形成：

```text
方向
 ↓
目标
 ↓
状态
 ↓
策略
 ↓
计划
 ↓
行动
 ↓
反馈
 ↓
复盘
 ↓
决策
 ↓
实验
 ↓
迭代
 ↓
新的策略
```

因此，2.4 解决的是：

> **Personal OS 中“有哪些模块，以及这些模块各自负责什么”。**

下一节 **2.5.核心运行流程** 将在此基础上继续解决：

> **这些模块究竟按照什么顺序运行，以及 Personal OS 在一天、一周、一个月和一次系统迭代中是怎样运行的。**

## 2.5.核心运行流程

## **2.5.核心运行流程**

本节定义 Personal OS 在实际运行中的主要流程。

2.4 已经确定了各模块“负责什么”，本节进一步确定：

> **这些模块按照什么顺序运行？**

Personal OS 不是一次性生成计划后结束的系统，而是一个持续运行的闭环系统。

其核心运行逻辑为：

```text
目标
 ↓
状态
 ↓
决策
 ↓
计划
 ↓
行动
 ↓
记录
 ↓
反馈
 ↓
复盘
 ↓
调整
 ↓
再次行动
```

同时，系统还存在更高层次的演化循环：

```text
观察
 ↓
诊断
 ↓
提出假设
 ↓
实验
 ↓
评估
 ↓
更新
 ↓
部署
 ↓
再次观察
```

因此，Personal OS 同时具有：

- 日运行循环
- 周运行循环
- 月运行循环
- 系统演化循环

不同循环处理不同时间尺度的问题。

------

### **2.5.1 核心运行闭环**

Personal OS 最基本的运行单元可以抽象为：

```text
State
 ↓
Decision
 ↓
Plan
 ↓
Execution
 ↓
Feedback
 ↓
Evaluation
 ↓
Adjustment
 ↓
New State
```

其中：

```text
State
=
当前状态

Decision
=
基于当前状态进行判断

Plan
=
将决策转化为具体计划

Execution
=
实际行动

Feedback
=
现实结果

Evaluation
=
比较目标、计划和现实

Adjustment
=
根据反馈进行调整

New State
=
行动之后形成的新状态
```

这意味着系统不是：

```text
制定计划
↓
执行计划
↓
结束
```

而是：

```text
制定计划
↓
执行
↓
观察现实
↓
发现偏差
↓
分析原因
↓
调整
↓
继续运行
```

因此：

> **Personal OS 的基本单位不是“计划”，而是“闭环”。**

------

### **2.5.2 单次行动运行流程**

最小运行单位可以是一项 Task 或一次具体行动。

```text
Goal
 ↓
Strategy
 ↓
Plan
 ↓
Task
 ↓
Start
 ↓
Execution
 ↓
Result
 ↓
Event
 ↓
Feedback
```

例如：

```text
Goal：
提高数学能力

↓

Strategy：
知识体系 + 题目训练

↓

Weekly Plan：
完成线性代数第一阶段

↓

Daily Plan：
学习线性代数 2 小时

↓

Task：
完成某章节学习与习题

↓

Execution：
实际学习 1.5 小时

↓

Result：
完成部分任务

↓

Event：
任务未完全完成

↓

Feedback：
记录执行偏差
```

此时系统不应该直接判断：

> “用户执行力差。”

而应该把这一结果送入 Feedback 与 Review 流程。

------

### **2.5.3 日运行流程**

日运行是 Personal OS 最高频的运行循环。

可以抽象为：

```text
开始一天
 ↓
读取当前状态
 ↓
读取当前目标与优先级
 ↓
生成 / 调整 Daily Plan
 ↓
执行 Task
 ↓
记录现实
 ↓
更新 State / Event
 ↓
继续执行
 ↓
日终 Review
 ↓
生成反馈
 ↓
为下一天提供输入
```

因此，一个完整的日运行流程可以表示为：

```text
┌────────────────────┐
│ 读取当前 State      │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ 读取 Goal/Priority  │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ 生成 Daily Plan     │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ Execution           │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ Event / Feedback    │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ State 更新          │
└─────────┬──────────┘
          ↓
┌────────────────────┐
│ Daily Review        │
└─────────┬──────────┘
          ↓
      下一天
```

------

### **2.5.4 Daily Plan 生成流程**

Daily Plan 不应该简单按照固定模板生成，而应该综合：

```text
Goal
+
Priority
+
State
+
Resource
+
Constraint
+
Strategy
+
已有任务
```

形成：

```text
Daily Plan
```

例如：

```text
当前目标
↓
本周目标
↓
今天的重点
↓
当前可用时间
↓
当前精力与专注状态
↓
现实约束
↓
生成今日计划
```

因此：

> **计划应该适应现实，而不是要求现实无条件适应计划。**

------

### **2.5.5 日间动态调整流程**

Daily Plan 生成后并不是固定不变的。

如果现实状态发生变化：

```text
计划执行中
 ↓
现实状态变化
 ↓
触发重新评估
 ↓
判断是否需要调整
 ↓
调整剩余任务
 ↓
继续执行
```

例如：

```text
原计划：
下午完成 3 个学习任务

↓

现实：
临时出现重要事务

↓

剩余可用时间下降

↓

系统重新计算

↓

保留最高优先级任务
↓
推迟低优先级任务
↓
重新形成剩余计划
```

这里必须遵循：

> **动态调整计划，不等于修改长期目标。**

------

### **2.5.6 日终 Review 流程**

一天结束后，系统进入 Daily Review。

基本流程：

```text
计划
 ↓
实际执行
 ↓
比较偏差
 ↓
记录问题
 ↓
判断原因
 ↓
形成结论
```

主要比较：

```text
Planned
vs
Actual
```

例如：

```text
计划学习：4h
实际学习：3h

偏差：-1h
```

此时系统继续分析：

```text
为什么少 1h？
```

可能进一步出现：

```text
时间不足
精力不足
任务估计错误
环境干扰
临时事件
执行问题
```

日终 Review 的重点不是：

> “今天完成率多少？”

而是：

> **“今天发生了什么，以及它对明天有什么意义？”**

------

### **2.5.7 周运行流程**

Weekly Cycle 用于处理单日无法识别的问题。

其基本流程：

```text
收集 7 天数据
 ↓
Weekly Review
 ↓
比较目标与实际
 ↓
识别偏差
 ↓
识别趋势
 ↓
判断问题类型
 ↓
调整下一周 Plan
```

完整流程：

```text
Daily Data
   ↓
Daily Review
   ↓
7 天数据汇总
   ↓
Weekly Review
   ↓
Trend Analysis
   ↓
Problem Identification
   ↓
Strategy / Plan Adjustment
   ↓
Next Week Plan
```

------

### **2.5.8 Weekly Review 的分析内容**

Weekly Review 至少应检查：

```text
1. 目标完成情况
2. 计划完成情况
3. 实际执行情况
4. 主要偏差
5. 状态变化
6. 时间资源使用情况
7. 任务延期情况
8. 主要问题
9. 下一周调整
```

同时应区分：

```text
目标问题
计划问题
策略问题
执行问题
资源问题
环境问题
状态问题
```

例如：

```text
计划完成率低
```

不能直接得出：

```text
执行力差
```

而应该继续分析：

```text
计划是否过量？
时间是否不足？
任务难度是否估计错误？
环境是否发生变化？
状态是否下降？
执行过程中是否存在阻力？
```

------

### **2.5.9 周计划生成流程**

下一周计划基于：

```text
Current Goal
+
Current Priority
+
Weekly Review
+
Current State
+
Available Resources
+
Constraints
+
Current Strategy
```

形成：

```text
Next Weekly Plan
```

其结构为：

```text
长期目标
 ↓
阶段目标
 ↓
本周复盘结果
 ↓
下一周重点
 ↓
Weekly Plan
 ↓
Daily Plans
```

------

### **2.5.10 月运行流程**

月运行用于观察比周周期更稳定的变化。

基本流程：

```text
收集本月数据
 ↓
Monthly Review
 ↓
分析长期趋势
 ↓
检查目标进展
 ↓
检查 Strategy
 ↓
检查执行稳定性
 ↓
决定下月重点
```

可以进一步观察：

```text
学习趋势
睡眠趋势
运动趋势
执行率趋势
时间利用趋势
任务延期趋势
专注趋势
习惯稳定性趋势
```

------

### **2.5.11 Monthly Review 的主要作用**

Monthly Review 不应该简单地变成：

> “这个月完成了多少任务？”

而应该观察：

> **“这个月的我发生了什么变化？”**

因此应重点检查：

```text
能力是否提高
行为是否变化
习惯是否稳定
目标是否推进
策略是否有效
计划是否现实
系统是否健康
```

这与 Personal OS 的长期目标一致：

> **系统不仅记录用户完成了什么，还要长期观察用户本人正在发生什么变化。**

------

### **2.5.12 日、周、月三级循环关系**

三级循环之间不是互相独立的。

其关系为：

```text
Daily Cycle
 ↓
产生每日数据
 ↓
Weekly Cycle
 ↓
产生周级趋势
 ↓
Monthly Cycle
 ↓
产生长期趋势
```

同时：

```text
Monthly Review
 ↓
影响 Strategy
 ↓
影响 Weekly Planning
 ↓
影响 Daily Planning
```

因此：

```text
日循环
=
执行层

周循环
=
纠偏层

月循环
=
策略观察层
```

------

### **2.5.13 异常与恢复流程**

Personal OS 必须允许运行失败。

例如：

```text
连续三天没有完成计划
```

系统不应该：

```text
计划失败
 ↓
系统停止
```

而应该：

```text
异常检测
 ↓
进入恢复模式
 ↓
分析原因
 ↓
判断问题级别
 ↓
降低或调整当前计划
 ↓
恢复基本运行
 ↓
继续观察
```

------

### **2.5.14 Recovery Mode**

Recovery Mode 用于：

> **系统出现明显运行异常，但还不需要改变核心策略。**

例如：

```text
连续三天执行率明显下降
```

系统可以：

```text
减少非核心任务
↓
保护重要任务
↓
降低短期计划负荷
↓
恢复基本作息
↓
观察未来几天状态
```

Recovery Mode 的目的不是降低长期要求，而是：

> **先恢复系统运行能力，再进行进一步诊断。**

------

### **2.5.15 Diagnostic Mode**

如果问题持续存在，则进入 Diagnostic Mode。

例如：

```text
连续三周：
计划完成率持续较低
任务延期率持续升高
疲劳持续增加
```

系统进入：

```text
Diagnostic Mode
```

流程：

```text
发现持续异常
 ↓
收集相关数据
 ↓
寻找共同因素
 ↓
提出问题
 ↓
建立假设
 ↓
设计验证方案
```

例如：

```text
问题：
计划完成率长期只有 65%

↓

假设 A：
任务总量过高

假设 B：
任务时间估计不准确

假设 C：
下午认知效率下降

假设 D：
环境干扰严重
```

然后进入实验或进一步观察。

------

### **2.5.16 Experiment Loop**

实验是 Personal OS 进行策略优化的重要机制。

基本流程：

```text
Observation
 ↓
Problem
 ↓
Hypothesis
 ↓
Experiment Design
 ↓
Experiment
 ↓
Data Collection
 ↓
Evaluation
 ↓
Decision
```

例如：

```text
Observation：
下午学习效率持续较低

↓

Hypothesis：
下午不适合安排高认知负荷任务

↓

Experiment：
连续两周把高认知任务调整到上午

↓

Data：
比较实验前后执行情况

↓

Evaluation：
分析变化

↓

Decision：
是否进入正式 Strategy
```

这样系统不会因为一次偶然情况就改变长期规则。

------

Personal OS 的最高级循环是系统自身的演化。

```text

 ↓

 ↓
Experiment
 ↓
Evaluate
 ↓
Update
 ↓
Deploy
 ↓
Observe
```

具体可以表示为：

```text

       ↓

       ↓
┌──────────────┐
```

### **2.5.21 核心运行原则**

#### **原则 1：系统必须持续运行**

Personal OS 不是一次性生成计划，而是持续运行的系统。

------

#### **原则 2：计划可以变化**

计划应当根据现实状态动态调整。

------

#### **原则 3：目标不能因为短期失败自动改变**

单次计划失败不等于目标错误。

------

#### **原则 4：失败首先进入反馈与诊断**

不能直接将失败解释为“用户能力不足”。

------

#### **原则 5：长期变化才能影响策略**

Strategy 的修改应该建立在长期数据、复盘或实验基础上，而不是单次异常。

------

#### **原则 6：系统必须允许恢复**

短期运行失败时，优先进入 Recovery Mode，而不是让系统失效。

------

#### **原则 7：系统自身的变化必须经过验证**

重要 Strategy、Policy 和系统规则不能无条件自动修改。

------

#### **原则 8：越靠近 Core，循环周期越长，修改门槛越高**

可以抽象为：

```text
Core
=
长期稳定

Goal
=
长期 / 中期

Strategy
=
中期

Plan
=
短期

Execution
=
即时
```

越靠近 Execution：

```text
变化快
调整灵活
```

越靠近 Core：

```text
变化慢
修改谨慎
```

------

Personal OS 的运行不是一条直线，而是多个嵌套循环：

```text

        ↓
日循环
        ↓
周循环
        ↓
月循环
        ↓
实验循环
        ↓
系统演化循环
        ↓
重新进入日 / 周 / 月循环
```

最终形成：

```text
现实
 ↓
观察
 ↓
判断
 ↓
计划
 ↓
行动
 ↓
反馈
 ↓
复盘
 ↓
调整
 ↓
再次行动
```

以及更高层的：

```text
观察
 ↓
诊断
 ↓
假设
 ↓
实验
 ↓
评估
 ↓
更新
 ↓
部署
 ↓
再次观察
```

因此，Personal OS 并不是一个：

> **“帮用户制定一套完美计划”的软件。**

而是一个：

> **能够持续观察现实、根据反馈行动、发现问题、进行诊断、验证方案并不断改进自身运行方式的个人闭环系统。**

至此：

```text

=
系统由什么构成

2.2 子系统划分
=
系统分成哪些模块

2.3 核心数据模型
=
系统处理哪些核心对象

2.4 模块职责与接口
=
各模块负责什么

2.5 核心运行流程
=
这些模块如何持续运行
```

下一节 **2.6.权限与变更机制** 将进一步解决：

> **谁可以修改什么？什么修改需要确认？什么修改可以自动进行？系统如何保证不会因为自动迭代而失控？**

## 2.6.权限与变更机制



## **2.6.权限与变更机制**

本节定义 Personal OS 中不同对象的修改权限，以及系统发生变化时应遵循的流程。

前面的设计已经确定：

> **上层约束下层，下层不能随意改变上层。**

同时：

> **用户拥有最终决定权。**

因此，Personal OS 必须同时解决两个问题：

```text
谁可以修改？
```

以及：

```text
修改应该如何发生？
```

本节不讨论具体的身份认证、数据库权限实现，而是先定义系统层面的逻辑权限模型和变更规则。

------

### **2.6.1 权限设计总体原则**

Personal OS 的权限设计遵循以下原则：

```text
权限由数据层级决定
而不是由 AI 能力决定
```

也就是说：

> AI 能力很强，不代表 AI 拥有更高的系统权限。

系统应区分：

```text
读取
↓
分析
↓
建议
↓
修改
↓
批准
```

不同对象允许的操作不同。

------

### **2.6.2 系统分层与权限关系**

Personal OS 的核心层级：

```text
Layer 0
Core
核心价值 / 长期方向
        ↓
Layer 1
Principles
核心原则 / 底线
        ↓
Layer 2
Strategy
策略 / 系统设计
        ↓
Layer 3
Execution
计划 / 任务 / 行动
```

权限总体规律：

```text
越靠近 Core
↓
修改频率越低
修改门槛越高
人工参与程度越高

越靠近 Execution
↓
修改频率越高
调整越灵活
自动化程度越高
```

------

### **2.6.3 权限类型**

系统中的操作权限可以分为：

```text
READ
读取

ANALYZE
分析

PROPOSE
提出建议

EDIT
修改

APPROVE
批准

DEPLOY
正式生效
```

这几个权限并不等价。

例如：

```text
AI：
READ CoreValue
ANALYZE CoreValue
PROPOSE CoreValue 修改

但：

AI ≠ APPROVE CoreValue 修改
```

最终批准权属于用户。

------

### **2.6.4 Core 层权限**

Core 层包括：

- CoreValue
- 长期人生方向
- 最核心的长期约束

其原则是：

> **Core 不允许 AI 自行修改。**

AI 可以：

```text
读取
↓
分析
↓
提出建议
↓
说明修改原因
```

但不能：

```text
AI
↓
直接修改 Core
```

------

### **2.6.5 Principle 层权限**

Principle 是约束系统运行方式的长期原则。

例如：

```text
不以长期健康换取短期成果。

不因短期情绪轻易改变长期目标。

计划服务于目标，而不是目标服务于计划。
```

AI 可以发现：

> 某条 Principle 与长期数据存在冲突。

然后形成：

```text
Modification Proposal
```

但是正式修改必须：

```text
AI Proposal
↓
用户审查
↓
用户批准
↓
生成 ChangeLog
↓
形成新版本
↓
正式生效
```

------

### **2.6.6 Strategy 层权限**

Strategy 是可以根据现实反馈进行调整的系统设计层。

例如：

```text
学习 Strategy
运动 Strategy
时间管理 Strategy
复习 Strategy
```

Strategy 的修改权限比 Principle 高。

AI 可以：

```text
发现问题
↓
分析原因
↓
提出 Strategy 修改方案
```

在符合既定权限和确认规则的情况下，可以由用户批准后更新。

Strategy 的修改必须能够追溯：

```text
旧 Strategy
↓
问题
↓
证据
↓
修改原因
↓
新 Strategy
↓
结果
```

------

### **2.6.7 Execution 层权限**

Execution 层包括：

- Daily Plan
- Task
- Habit 的执行安排
- 当前行动

这是系统中最灵活的一层。

允许根据实时状态进行动态调整：

```text
Task 顺序调整
Task 时间调整
Task 延期
Task 合并
Task 拆分
低优先级任务取消
```

例如：

```text
临时事件发生
↓
剩余时间减少
↓
重新安排 Daily Plan
```

这类修改不需要改变 Strategy 或 Goal。

------

### **2.6.8 权限矩阵**

可以将核心对象的权限关系整理为：

| 对象           | 用户读取 | AI读取 | AI分析 | AI建议     | AI直接修改 | 用户确认 |
| -------------- | -------- | ------ | ------ | ---------- | ---------- | -------- |
| CoreValue      | ✓        | ✓      | ✓      | ✓          | ×          | ✓        |
| Principle      | ✓        | ✓      | ✓      | ✓          | ×          | ✓        |
| Long-term Goal | ✓        | ✓      | ✓      | ✓          | ×          | ✓        |
| 阶段 Goal      | ✓        | ✓      | ✓      | ✓          | ×/有限     | ✓        |
| Priority       | ✓        | ✓      | ✓      | ✓          | 可有限调整 | ✓        |
| Strategy       | ✓        | ✓      | ✓      | ✓          | ×/按规则   | ✓        |
| Policy         | ✓        | ✓      | ✓      | ✓          | ×/按规则   | ✓        |
| Plan           | ✓        | ✓      | ✓      | ✓          | ✓/按规则   | 可选     |
| Task           | ✓        | ✓      | ✓      | ✓          | ✓          | 可选     |
| Habit          | ✓        | ✓      | ✓      | ✓          | ✓/按规则   | 可选     |
| Event          | ✓        | ✓      | ✓      | 可辅助生成 | ×          | 可修正   |
| Observation    | ✓        | ✓      | ✓      | ✓          | 可生成草稿 | ✓        |
| Metric         | ✓        | ✓      | ✓      | ✓          | 按数据规则 | —        |
| Review         | ✓        | ✓      | ✓      | ✓          | 可生成草稿 | ✓        |
| Decision       | ✓        | ✓      | ✓      | ✓          | ×          | ✓        |
| Experiment     | ✓        | ✓      | ✓      | ✓          | ×/按规则   | ✓        |
| Version        | ✓        | ✓      | ✓      | ✓          | ×          | ✓        |
| ChangeLog      | ✓        | ✓      | ✓      | ✓          | ×/追加     | ✓        |

其中：

> **AI 是否能够直接修改，不仅取决于对象，还取决于具体修改类型。**

默认情况下，高层对象禁止 AI 直接修改。

------

### **2.6.9 自动修改与人工确认的边界**

系统不能简单地把所有修改都规定成：

> “必须人工确认。”

否则系统会变得非常低效。

因此应当区分：

```text
低风险 / 高频 / 可逆
```

和：

```text
高风险 / 低频 / 不可逆
```

例如：

```text
Daily Task 时间调整
=
低风险

长期 Strategy 修改
=
高风险
```

因此：

```text
Execution 层
→ 可以高度自动化

Strategy 层
→ 需要较强约束

Principle 层
→ 必须人工确认

Core 层
→ 用户主动修改
```

------

### **2.6.10 自动调整的条件**

系统允许自动调整的修改必须满足：

```text
1. 修改范围属于低层级对象
2. 修改可逆
3. 不改变长期目标
4. 不违反 Principle
5. 不改变核心数据
6. 有明确触发规则
7. 修改结果可记录
```

例如：

```text
IF
今天剩余时间减少

THEN
调整低优先级 Task 的时间
```

这种行为可以自动执行。

------

### **2.6.11 禁止自动修改的对象**

以下对象原则上不得由 AI 自动修改：

```text
CoreValue
Principle
核心长期方向
重大人生目标
重大人生决策
系统最高级规则
```

即使 AI 认为：

> “修改之后系统表现会更好。”

也只能：

```text
提出 Proposal
↓
等待用户决定
```

------

### **2.6.12 变更请求机制**

任何重要修改都不应直接覆盖原对象。

应产生：

```text
Change Request
```

基本结构：

```text
Change Request
│
├── Target
├── Current Value
├── Proposed Value
├── Reason
├── Evidence
├── Expected Effect
├── Risk
├── Reversibility
└── Approval
```

例如：

```text
Target：
Study Strategy

Current：
每天安排固定 5 小时学习

Evidence：
过去 21 天完成率持续低于预期

Proposal：
调整为每日 4 小时核心学习 + 弹性任务

Expected Effect：
提高计划完成率

Risk：
可能降低理论学习总量

Approval：
待用户确认
```

------

### **2.6.13 变更生命周期**

正式变更应遵循：

```text
发现问题
 ↓
提出 Change Request
 ↓
分析影响
 ↓
提出修改方案
 ↓
用户 / 系统审核
 ↓
批准
 ↓
生成新版本
 ↓
部署
 ↓
观察结果
```

可以表示为：

```text
Draft
 ↓
Review
 ↓
Approved
 ↓
Applied
 ↓
Observed
 ↓
Accepted / Reverted
```

------

### **2.6.14 Version 机制**

Personal OS 必须具有版本概念。

例如：

```text
v0.1
v0.2
v0.3
v1.0
v1.1
v2.0
```

每一个重要版本都应该记录：

```text
Version
├── Version Number
├── Parent Version
├── Changes
├── Reason
├── Evidence
├── Approval
├── Effective Time
└── Result
```

这样系统能够回答：

> **当前运行的是什么版本？**

> **为什么变成这个版本？**

------

### **2.6.15 版本修改原则**

版本升级不是因为：

> “AI 想试一下新的方法。”

而应该有明确依据。

例如：

```text
Version: v1.3

Problem:
计划完成率长期较低

Evidence:
过去 21 天实际数据

Hypothesis:
任务总量过高

Change:
调整 Strategy

Experiment:
14 days

Expected Result:
计划完成率提高
```

实验结果确认后，再决定：

```text
Merge
```

或者：

```text
Reject
```

------

### **2.6.16 回滚机制**

任何重要系统修改都必须具备回滚能力。

例如：

```text
v1.2
 ↓
v1.3
 ↓
发现问题
 ↓
Rollback
 ↓
v1.2
```

回滚并不意味着：

> “系统失败。”

而是：

> **实验结果证明当前修改不适合现阶段，因此恢复到经过验证的稳定版本。**

------

### **2.6.17 稳定版本与实验版本**

可以进一步借鉴 Git 的思想。

```text
Personal OS
│
├── stable
│
├── experiment
│
└── archive
```

其中：

```text
stable
=
当前正式运行版本

experiment
=
正在测试的新方案

archive
=
历史版本
```

例如：

```text
stable
v1.2

experiment
v1.3-experiment

测试 14 天

↓

结果评估

↓

merge
```

或者：

```text
实验失败
↓
discard
```

这样实验不会直接破坏正式运行系统。

------

### **2.6.18 AI Proposal 机制**

AI 对系统进行重要修改时，应优先生成：

```text
Proposal
```

而不是直接执行。

Proposal 至少包含：

```text
问题
↓
证据
↓
分析
↓
假设
↓
建议修改
↓
预期结果
↓
风险
↓
验证方法
```

例如：

```text
Proposal：

发现过去 3 周晚间学习效率持续下降。

Hypothesis：
晚间认知负荷过高。

Proposal：
将部分高认知任务转移至上午。

Experiment：
测试 14 天。

Expected Result：
晚间疲劳下降，整体执行率提高。
```

------

### **2.6.19 用户批准机制**

对于重要修改：

```text
AI Proposal
 ↓
User Review
```

用户需要能够看到：

```text
为什么改
改什么
有什么证据
可能有什么副作用
如何验证
如何回滚
```

然后选择：

```text
Approve
Reject
Modify
Postpone
```

------

### **2.6.20 变更影响分析**

重要修改不能只考虑目标对象本身，还应该分析：

```text
这个修改会影响什么？
```

例如修改 Strategy：

```text
Strategy
 ↓
Weekly Plan
 ↓
Daily Plan
 ↓
Task
 ↓
Execution
 ↓
Metric
```

因此修改 Strategy 可能产生连锁影响。

系统在批准之前应尽可能显示：

```text
Affected Objects
```

例如：

```text
修改 Strategy A

可能影响：
├── 3 个 Projects
├── 12 个 Tasks
├── 2 个 Habits
└── 当前 Weekly Plan
```

------

### **2.6.21 变更的可追溯性**

系统必须能够从结果反向追踪：

```text
当前结果
 ↓
当前 Strategy
 ↓
Strategy 的 Version
 ↓
对应 ChangeLog
 ↓
当时的 Decision
 ↓
当时的 Evidence
 ↓
更早的 Version
```

也可以反向：

```text
一个 Decision
↓
产生什么修改
↓
影响了什么
↓
最终结果如何
```

这样 Personal OS 才真正具有工程意义上的：

> **可追溯性。**

------

### **2.6.22 核心数据保护**

以下数据原则上不能因为系统优化而被无痕删除：

```text
历史 Event
历史 Observation
历史 Metric
历史 Review
历史 Decision
历史 Experiment
历史 Version
历史 ChangeLog
```

因为：

> **历史数据本身就是 Personal OS 的记忆。**

如果系统能够任意修改自己的历史，那么之后的复盘、趋势分析和版本追踪都可能失去意义。

------

### **2.6.23 系统自修改的安全边界**

Personal OS 虽然具备自我迭代能力，但不能无限制地自行修改自身。

必须遵循：

```text
系统可以：
发现问题
↓
分析问题
↓
提出假设
↓
设计实验
↓
验证方案
↓
提出修改
```

但不能：

```text
系统自行定义新的 Core
↓
系统自行降低 Principle
↓
系统自行修改长期目标
↓
系统自行宣布自己运行良好
```

尤其必须防止：

```text
原目标
↓
无法完成
↓
系统降低目标
↓
完成率提高
↓
系统判断自己优化成功
```

这种情况下：

> **指标被优化了，但人的真实结果没有改善。**

因此：

> **评价系统的规则本身不能被同一个系统无约束地修改。**

------

### **2.6.24 “不可变层”设计**

为避免系统自我修改导致目标漂移，Personal OS 必须存在不可变或高度受保护的层。

可以表示为：

```text
Layer 0
Core Values
不可由 AI 自行修改
        ↓
Layer 1
Principles
需要用户批准
        ↓
Layer 2
Strategy
AI 可以提出修改
用户确认后生效
        ↓
Layer 3
Execution
允许动态调整
```

这形成一个：

> **Immutable / Protected Core**

它是整个系统稳定性的基础。

------

### **2.6.25 权限与运行流程的关系**

权限机制必须嵌入 2.5 的运行流程，而不是独立存在。

例如：

```text
Execution Failure
 ↓
Feedback
 ↓
Review
 ↓
发现 Strategy 可能存在问题
 ↓
AI Proposal
 ↓
Permission Check
 ↓
User Approval
 ↓
New Version
 ↓
Deploy
```

因此：

> **运行流程决定“什么时候需要改变”，权限机制决定“谁有资格改变”。**

------

### **2.6.26 变更失败处理**

系统变更后，如果结果不符合预期：

```text
New Version
 ↓
Observation
 ↓
Result 不符合预期
```

系统可以：

```text
继续观察
```

或者：

```text
进入 Review
```

必要时：

```text
Rollback
```

而不应该因为一次实验失败就认为整个 Personal OS 设计失败。

------

### **2.6.27 权限机制的最终原则**

Personal OS 的权限体系最终可以概括为：

```text
Core
=
用户拥有最终控制权

Principles
=
用户确认

Strategy
=
AI 分析 + 用户批准

Plan
=
可以动态调整

Execution
=
高度灵活

Historical Data
=
尽量不可篡改

Version
=
可追踪

Change
=
可解释

Experiment
=
可验证

Rollback
=
始终保留
```

最终形成：

```text
能力越高
≠
权限越高

AI 越强
≠
AI 越能决定

系统越自动化
≠
用户越没有控制权
```

而应该是：

```text
AI
=
分析与建议

Personal OS
=
规则与执行

Human
=
最终控制
```

------

### **2.6.28 本节总结**

至此，Personal OS 的权限与变更机制可以概括为：

```text
用户
 ↓
拥有最终决定权

AI
 ↓
观察 / 分析 / 提议

系统
 ↓
按照权限规则执行

版本系统
 ↓
记录变化

实验系统
 ↓
验证变化

回滚机制
 ↓
防止错误变化持续存在
```

整个变更闭环为：

```text
发现问题
 ↓
分析
 ↓
提出 Proposal
 ↓
权限检查
 ↓
人工确认
 ↓
建立 Version
 ↓
部署
 ↓
观察
 ↓
评估
 ↓
接受 / 回滚
```

而整个权限体系最重要的一条原则是：

> **Personal OS 可以自我改进，但不能自行重新定义“为什么存在”。**

因此：

```text
Core
限制方向

Principles
限制行为

Strategy
决定方法

Plan
决定安排

Execution
负责行动

AI
负责智能辅助

User
拥有最终决定权
```

这使 Personal OS 同时具备：

- 自动化能力
- 自我迭代能力
- 可解释性
- 可追溯性
- 可恢复性
- 用户主权

并避免系统在长期运行过程中出现**目标漂移、权限失控和“为了提高指标而修改指标”**的问题。

### **2.7.5 为什么选择 C++**

C++ 作为 Personal OS 的核心编程语言。

主要原因包括：

- 高性能
- 较低运行时开销
- 良好的本地计算能力
- 对桌面系统具有较强控制能力
- 与 Qt 具有成熟的配套关系
- 适合构建长期运行的原生桌面应用
- 适合实现复杂的数据处理与系统逻辑

Personal OS 的核心业务逻辑全部以 C++ 为基础实现。

因此：

> **Personal OS 不依赖 Python 作为核心后端语言。**

------

### **2.7.6 为什么选择 Qt**

Qt 负责 Personal OS 的桌面 UI 与相关应用能力。

采用：

```text
Qt 6
+
Qt Quick
+
QML
```

而不是以传统 Qt Widgets 作为主要界面技术。

主要原因：

- 适合现代桌面 UI
- 支持动画与动态交互
- 支持硬件加速
- UI 与业务逻辑可以分离
- QML 适合快速构建复杂界面
- C++ 与 Qt 之间具有成熟的集成方式

因此：

```text
C++
=
系统逻辑

QML
=
界面表现

Qt
=
二者之间的应用框架
```

### **2.7.16 AI 数据边界**

AI Engine 不应默认访问整个数据库。

应采用：

```text

 ↓

 ↓

```

> “为什么我最近学习效率下降？”

系统只提供相关：

```text

```

而不是：

```text

```

这样能够减少：

- 隐私风险
- Token 消耗
- 无关信息干扰
- 上下文噪音
